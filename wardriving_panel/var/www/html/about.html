The project: WETO-WARDRIVING Ecosystem

This ecosystem was born out of a curiosity to audit and visualize the Wi-Fi spectrum autonomously and with geolocation. The hardware core initially utilized a CYD (Cheap Yellow Display); however, due to its technical limitations, achieving precise and fully automated auditing was impossible. Consequently, the project was migrated to a Raspberry Pi—specifically the Raspberry Pi Zero 2 W paired with a USB Wi-Fi dongle featuring the MTK7601 chipset (monitor mode compatible), a serial GPS receiver (M8L), and three 4000mAh Li-Po batteries connected in parallel via a TC4056A module. This setup provides the Raspberry Pi with approximately 20 hours of battery life under the project's specific workload. The work flow is the following:

1.- GPS Capture gpsd receives NMEA data from the GPS receiver connected to /dev/ttyAMA0. The wardriving.sh script continuously reads from gpspipe and writes the latest valid position (mode > 1)—including latitude, longitude, and timestamp—to a temporary file..
2.- GPS Signal Monitor (LED) The gpscheck service monitors the GPS mode in real-time and indicates the status via the Raspberry Pi's ACT LED: off (no signal), slow blink (Mode 1), fast blink (2D fix), or solid on (3D fix).
3.- Wi-Fi Network Capture wardriving.sh sets the wlan1 interface to monitor mode and launches a background channel hopper that cycles through channels 1-13 every 0.5 seconds. Simultaneously, tshark captures beacon frames (subtype 0x08), extracting BSSID, SSID, RSSI, channel, AKM, and privacy flags.
4.- Beacon Processing and Enrichment For each captured beacon, the script discards those lacking a GPS fix, decodes the SSID from hex, maps the AKM/PCS fields to security labels (WPA2, WPA3, WEP, OPEN…), identifies encryption (AES, TKIP…), and queries the MariaDB mac_cache table to resolve the vendor based on the BSSID’s OUI prefix.
5.- Database Persistence The enriched data is inserted into the MariaDB wifi_networks table using an INSERT … ON DUPLICATE KEY UPDATE statement. This updates the position, RSSI, security, and vendor only if the new RSSI is stronger than the previously recorded value.
6.- Reverse Geolocation localization.py queries entries in wifi_networks that have coordinates but lack assigned street or city information. For each entry, it searches a SQLite database (calles.sqlite with SpatiaLite) for the nearest street and corresponding city, then updates the record in MariaDB.
7.- Web Service and Visualization Apache serves static HTML pages, while get_data.php and status_api.php act as the API, querying MariaDB and returning JSON. The web pages consume these endpoints to display a paginated, searchable network list (index.html), an interactive map with clusters and filters (map.html), statistical charts (graficos.html), and a real-time system status dashboard (status.html).
8.- System Monitoring status.html refreshes every 3 seconds by polling status_api.php, which returns CPU/RAM/uptime metrics, GPS status, database totals, security distribution, channel usage, top cities, and the status of active processes (tshark, wardriving.sh, channel hopper, and wlan1 mode).
